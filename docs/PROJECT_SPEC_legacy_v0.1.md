## 0. Πώς διαβάζεται αυτό το αρχείο

Το `PROJECT_SPEC.md` είναι η **ενιαία πηγή αλήθειας** για τον σχεδιασμό και την ανάπτυξη. Κάθε νέα απόφαση ενημερώνεται εδώ και στον σχετικό έλεγχο αποδοχής **πριν** ενσωματωθεί η αλλαγή στην παραγωγή.

**Ετικέτες:**
- **[ΑΠΟΦΑΣΙΣΤΗΚΕ]** — συγκεκριμένη απαίτηση που έχει εγκριθεί.
- **[ΠΡΩΤΗ ΔΟΚΙΜΗ]** — αντικείμενο της πρώτης λειτουργικής δοκιμαστικής έκδοσης· δεν συνεπάγεται παραγωγική ετοιμότητα.
- **[ΑΝΑΜΟΝΗ ΚΩΔΙΚΑ]** — απαιτεί επιθεώρηση πραγματικού υπάρχοντος project πριν υλοποιηθεί πλήρως.
- **[ΑΡΓΟΤΕΡΑ]** — σκόπιμα εκτός πρώτης έκδοσης, αλλά προβλέπεται αρχιτεκτονικά.
- **[ΑΝΟΙΧΤΟ]** — ουσιαστική λεπτομέρεια που μένει να αποφασιστεί.

**Ονομασίες που ΔΕΝ πρέπει να συγχέονται:**
- **«Πίνακας Οργανωτικού»**: ο κεντρικός, συνεχώς διαθέσιμος, επεξεργάσιμος πίνακας φοιτητών.
- **«Οργανωτικό» (συνεδρίαση)**: συγκεκριμένη, χρονικά ορισμένη διαδικασία εξέτασης εγγραφών, με σταθερή λίστα και απολογισμό.
- **«Οργανωτικό» (εφαρμογή)**: η νέα κεντρική εφαρμογή που περιέχει τις παραπάνω λειτουργίες **και ολόκληρη τη λειτουργικότητα του Portal**.
- **«Portal»**: η ξεχωριστή εφαρμογή στελεχών, η οποία συνεχίζει να υπάρχει και μοιράζεται τις ίδιες υπηρεσίες.
- **«Dashboard ιστοσελίδας»**: το παλιό, *διαφορετικό* Netlify project για Μέλη, Bluepass, Προσφορές, Newsletter κ.λπ., με **άλλη βάση**. Δεν είναι το υπάρχον Portal.

## 1. Αδιαπραγμάτευτοι στόχοι

1. **Ευκολία και ταχύτητα τύπου Access/Excel**: πολλαπλά κελιά, πληκτρολόγιο, φίλτρα, Find/Replace, ελάχιστα κλικ. Καμία αναγκαστική μετάβαση σε ξεχωριστή φόρμα για την καθημερινή επεξεργασία.
2. **Καθαρό, επαγγελματικό, μινιμαλιστικό UI**: άνετη τυπογραφία, ήσυχο χρωματικό σύστημα, χωρίς άσκοπες κινήσεις, gradients, οπτικό θόρυβο, καρτέλες στατιστικών όπου δεν χρειάζονται.
3. **Ισχυρές λειτουργίες στο παρασκήνιο**: σύνθετα φίλτρα, συνεδριάσεις, ιστορικό, αναφορές, εξαγωγές, σύνδεση εφαρμογών, ασφαλή δικαιώματα.
4. **Διαρκής επεκτασιμότητα**: νέα modules, νέοι τύποι δεδομένων, ροές, αυτοματισμοί και αναφορές σε μεταγενέστερες εκδόσεις χωρίς ανακατασκευή των βασικών υποδομών.
5. **Μία λογική υλοποίηση ανά λειτουργία**: όχι ανεξάρτητο σύστημα οικονομικών/SMS/Bluepass για κάθε εφαρμογή. Κοινός κώδικας + κοινή βάση + κοινές υπηρεσίες, με δύο κατάλληλες διεπαφές.
6. **Ο ORGANOTIKOS δεν χρειάζεται ΠΟΤΕ να μπει στο Portal**: όλες οι δυνατότητες του Portal, συμπεριλαμβανομένων **οικονομικών, SMS, ομάδων, εργασιών και εκδηλώσεων**, λειτουργούν πλήρως μέσα στο περιβάλλον του Οργανωτικού.
7. **Σταθερότητα δεδομένων**: καμία αυθαίρετη αλλαγή της παραγωγής, κανένα demo με πραγματικούς φοιτητές, καμία μεταφορά χωρίς ελέγχους και backup.
8. **Συμμετοχή χρήστη στον σχεδιασμό**: στην έναρξη κατασκευής κάθε ενότητας να παρουσιάζεται και να εγκρίνεται η συγκεκριμένη εμπειρία χρήσης, ακόμη και λεπτομέρειες UI που επηρεάζουν καθημερινή εργασία. Όχι αυθαίρετα features· όχι ατέρμονες ερωτήσεις για αυτονόητα.

## 2. Τεχνική αρχιτεκτονική [ΑΠΟΦΑΣΙΣΤΗΚΕ]

| Στρώμα | Επιλογή | Σημειώσεις |

| Ταυτότητα | **Ένα Supabase Auth** | Ένας λογαριασμός και κοινή ταυτότητα και στις δύο εφαρμογές· διαφορετικά δικαιώματα ανά εφαρμογή. |

| Backups/jobs | **Υπάρχων Ubuntu server στο γραφείο (24/7)** | Προγραμματισμένα backups, περιοδικές αναφορές, jobs, επιλεγμένες βαριές εργασίες. |
| Production/staging | **Απομονωμένα περιβάλλοντα** | Πραγματικά δεδομένα μόνο στην παραγωγή· συνθετικά μόνο στο δοκιμαστικό περιβάλλον. |

### 2.1 Domains / εφαρμογές

- **Οργανωτικό**: δικό του domain/subdomain (ο ακριβής hostname δεν έχει οριστικοποιηθεί).
- **Portal**: παραμένει ξεχωριστό domain και περιβάλλον χρήστη.
- **Δημόσια ιστοσελίδα / φόρμες Members–Bluepass**: συνεχίζουν κατάλληλα· τελικός σχεδιασμός μετά από επιθεώρηση κώδικα.
- **Εκλογές/Γενικές Συνελεύσεις**: μελλοντικό εξειδικευμένο `vote.organotiko.com` [ΑΡΓΟΤΕΡΑ].
- **SMS**: **όχι τρίτο user-facing app ή ανεξάρτητο μενού**. Η ίδια υπηρεσία εμφανίζεται **και μέσα στο Portal και μέσα στο Οργανωτικό**, χωρίς ανακατεύθυνση του ORGANOTIKOS. Ο υπάρχων SMS service μπορεί να αξιοποιηθεί ή να μεταφερθεί εσωτερικά.

### 2.2 Αρχιτεκτονική κώδικα — προτεινόμενη οργάνωση

```text
repository/
├── apps/
│   ├── organotiko/            # κεντρική εφαρμογή
│   └── portal/                # εφαρμογή στελεχών
├── packages/
│   ├── domain/                # μοντέλα, επιχειρησιακοί κανόνες
│   ├── ui/                    # επαναχρησιμοποιήσιμα στοιχεία
│   ├── features/              # finances, SMS, events, members, κ.λπ.
│   ├── auth-permissions/      # κοινά policies και authorization helpers
│   └── data/                  # typed clients και repositories
├── supabase/
│   └── migrations/            # versioned database changes
├── server/
│   └── jobs/                  # Ubuntu backup/cron/job scripts
├── tests/
└── PROJECT_SPEC.md
```

Το σχήμα είναι **πρόταση δομής repo**, όχι εντολή να ξαναγραφτεί το υπάρχον Portal χωρίς έλεγχο. Οι αλλαγές στις κοινές λειτουργίες πρέπει να γίνονται **μία φορά στον κοινό κώδικα** και να εμφανίζονται στα δύο UIs.

### 2.3 Μη λειτουργικές απαιτήσεις

- Το Οργανωτικό είναι **online-only**, συμπεριλαμβανομένου mobile/PWA: χωρίς offline αποθήκευση ή deferred synchronization προσωπικών δεδομένων.
- Η απώλεια Internet εμφανίζεται καθαρά· μη επιβεβαιωμένη αποθήκευση **δεν εμφανίζεται ως επιτυχής**.
- Ο Ubuntu server **δεν πρέπει να είναι single point of failure** για τη ζωντανή λειτουργία των δύο εφαρμογών. Αν πέσει, προσωρινά σταματούν μόνον οι εξαρτώμενες περιοδικές εργασίες· υπάρχουν ειδοποιήσεις και επαναλήψεις.
- Desktop και mobile έχουν **τις ίδιες επιτρεπόμενες δυνατότητες**, με διαφορετική, πρακτική διάταξη. Από κινητό διατίθεται και ο πλήρης πίνακας όταν χρειάζεται.
- Κώδικας με TypeScript/React όπου είναι συμβατό με το υπάρχον Portal· οριστικές λεπτομέρειες μετά από code inspection.

## 3. Υπάρχοντα συστήματα και διαδικασία ενοποίησης

### 3.1 Access / κύριο Οργανωτικό

- Πηγή: `ΟΡΓΑΝΩΤΙΚΟ 2026 - 2027.accdb` και αντίστοιχη εξαγωγή `ΟΡΓΑΝΩΤΙΚΟ.xlsx`.
- Σε προγενέστερη εξέταση: περίπου **2.057 εγγραφές, 52 πεδία**· **ο αριθμός επαληθεύεται από το πιο πρόσφατο αρχείο μεταφοράς**.
- Η καθημερινή εργασία σήμερα γίνεται σχεδόν αποκλειστικά σε έναν γρήγορο πίνακα/queries και μερικές φόρμες. Πρώτα διαφυλάσσεται αυτή η εμπειρία, μετά προστίθενται λειτουργίες.

### 3.2 Portal

- Υφιστάμενη υλοποίηση Cloudflare + Supabase (`ORGANOSI`) με χρήστες, ομάδες, εργασίες, εκδηλώσεις, οικονομικά, SMS και ιστορικά.
- Υπάρχει ιστορικό εκδόσεων/πακέτων Portal v2.1.x. **Ο ακριβής τελευταίος κώδικας, migrations, τρέχουσες ρυθμίσεις και παραγωγική κατάσταση πρέπει να ελεγχθούν**.
- Διατηρούνται **πλήρως** οι υπάρχουσες λειτουργίες στο Portal και αποκτούν αντίστοιχη πλήρη λειτουργία στο Οργανωτικό, μέσω κοινών modules.
- Δυσχρηστίες του σημερινού Portal θα διορθωθούν στη νέα κοινή υλοποίηση και **όχι με άσκοπα διπλά patches** στο παλιό σύστημα, εκτός από κρίσιμα προβλήματα.

### 3.3 Ξεχωριστό Netlify dashboard ιστοσελίδας [ΑΝΑΜΟΝΗ ΚΩΔΙΚΑ]

Υπάρχει σχεδόν ολοκληρωμένη ροή σε Google Sheets/Forms και ενδεχομένως Apps Script. **Δεν επανεφευρίσκεται ούτε μεταφέρεται στο πρώτο release**. Στην πρώτη δοκιμή οι σχετικές διαδρομές δείχνουν **«Υπό κατασκευή»**· μελλοντική επιθεώρηση και βελτιωμένη μεταφορά. Προβλέπονται εξαρχής επεκτάσιμα events/snapshots/roles, χωρίς πρόωρη υλοποίηση της ροής Vote.

### 3.5 Μεταφορά δεδομένων

1. Πλήρες backup και κατάσταση αναφοράς των τριών παλιών πηγών.
2. Inventory σχέσεων, IDs και ιστορικών· χαρτογράφηση source → target.
3. Ενιαίο εσωτερικό `person_id` (σταθερή ταυτότητα προσώπου) ανεξάρτητο από ΕΦΕΚΘ ΜΟΝΑΔΙΚΟΣ / ΑΔΤ / Portal `user_id`.
4. Matching suggestions με όνομα, παραλλαγές, τηλέφωνα, τμήμα και άλλα νόμιμα διαθέσιμα γνωρίσματα· **κανένα αυτοματοποιημένο αβέβαιο merge**.
5. Review/απόφαση από ORGANOTIKOS: συσχέτιση με υφιστάμενο πρόσωπο, διατήρηση διακριτών ή δημιουργία νέου.
6. Μεταφορά histories, statuses, σχέσεων, δικαιωμάτων και αναγνωριστικών όπου είναι αναγκαία.
7. Reconciliation: counts, foreign keys, εγγραφές ανά source, κενά, διπλοεγγραφές, ιστορικά συγκεντρωτικά.
8. Δοκιμές staging και rollback/cutover plan, **μόνο μετά production migration**.

**Ούτε τα λανθασμένα/διαφορετικά ελληνικά ονόματα ούτε το κοινό τηλέφωνο αποδεικνύουν ταυτότητα.** Υπάρχει side-by-side review και χειροκίνητη επιβεβαίωση.

## 4. Κεντρικός Πίνακας Οργανωτικού [ΑΠΟΦΑΣΙΣΤΗΚΕ]

### 4.1 Βασικό UX

- **Πρώτη και κυρίαρχη επιλογή** στη ναυσιπλοΐα. Access/Excel-like data grid με πολλές γραμμές και στήλες, όχι form-first UI.
- Άμεση επεξεργασία κελιών (`inline editing`), πληκτρολόγιο, εύκολη εναλλαγή γραμμών/στηλών, paste όπου ασφαλές.
- **Auto-save** μετά Enter/Tab/έξοδο από κελί· ευδιάκριτη αλλά διακριτική κατάσταση `saving/saved/failed`.
- Ποτέ αθόρυβη αποτυχία αποθήκευσης. Αν χαθεί η σύνδεση, δεν δηλώνουμε ψευδή επιτυχία.
- Ζωντανές αλλαγές άλλων χρηστών χωρίς manual refresh, με **προστασία σύγκρουσης στο ίδιο πεδίο** (optimistic concurrency, ορατή επίλυση). Επεξεργασία διαφορετικών πεδίων του ίδιου φοιτητή επιτρέπεται.
- Ελεύθερη απόκρυψη/επανεμφάνιση, αλλαγή σειράς και πλάτους στηλών. Sort/filter από επικεφαλίδες, συνδυασμοί σύνθετων κριτηρίων.
- Find & Replace και bulk edits/deletions με **προεπισκόπηση και σαφή επιβεβαίωση**.
- Εξαγωγή της τρέχουσας προβολής, διατηρώντας ορατές/φιλτραρισμένες εγγραφές και sort· εναλλακτική εξαγωγή ίδιων γραμμών με όλες τις επιτρεπόμενες στήλες.

### 4.2 Αποθηκευμένες προβολές

- Κατά αποθήκευση επιλογή **«Προσωπική»** ή **«Κοινή»** προβολή για εξουσιοδοτημένους χρήστες.
- Αποθήκευση φίλτρων, sorting, ορατών/κρυμμένων στηλών, σειράς και πλάτους.
- **«Ορισμός ως προεπιλεγμένη προβολή»** για **κάθε** χρήστη ξεχωριστά· επαναφορά αρχικής.
- Προσωπικές επιλογές **δεν αλλάζουν** τις προβολές άλλων χρηστών.
- Ενέργεια **«Δημιουργία Οργανωτικού από τα τρέχοντα φίλτρα»**: μεταφορά **ορισμών** φίλτρων σε νέο προσχέδιο συνεδρίασης, όχι άμεση παγωμένη λίστα.

### 4.3 Αναζήτηση και καρτέλα

- Ξεχωριστή **Γρήγορη Αναζήτηση**, ιδίως χρήσιμη στο κινητό: ονοματεπώνυμο, τηλέφωνα, τμήμα, έτος, Πυρήνας1, ΜΟΝΑΔΙΚΟΣ, ΑΔΤ και άλλα δομημένα επιτρεπόμενα πεδία.
- Αποτελέσματα: ονοματεπώνυμο, τμήμα, έτος, ΕΦΕΚΘ, Πυρήνας1, γρήγορο άνοιγμα καρτέλας.
- **Όχι αναζήτηση στο ελεύθερο πεδίο ΠΛΗΡΟΦΟΡΙΕΣ.**
- **Όχι συνημμένα αρχεία** στην καρτέλα φοιτητή.
- Φοιτητική καρτέλα με όλα τα διαθέσιμα επιτρεπόμενα πεδία, εύκολη διόρθωση και ιστορικό μόνο για το ελεύθερο πεδίο ΠΛΗΡΟΦΟΡΙΕΣ.

### 4.4 Data entry / διαγραφή / προσωπικές πληροφορίες

- Καταχώριση φοιτητή **έναν-έναν**, μερικά γνωστά στοιχεία επαρκούν. Πρώτα προτείνεται έλεγχος για πιθανές διπλοεγγραφές.
- Fuzzy duplicate suggestions· οργανωτικός επιλέγει τελικό merge και ανά πεδίο ποια τιμή κρατείται. Προστατεύονται συσχετίσεις και ιστορικά στατιστικά.
- Κανονικές εγγραφές κειμένου → **αυτόματα ΚΕΦΑΛΑΙΑ** (ελληνικά/λατινικά), εκτός από emails, passwords και άλλα πραγματικά case-sensitive πεδία. Αναζητήσεις accent/case insensitive.
- Αφαίρεση φοιτητή από ενεργό πίνακα με ασφαλή αρχειοθέτηση όπου επιτρέπεται, όχι αυθαίρετη διαγραφή ιστορικών καταμετρήσεων.
- Απόφοιτοι με έτος **0** σε αρχείο αποφοίτων· τιμητικά/πρώην στελέχη με **Π** μένουν στον ενεργό πίνακα.
- Ένα πεδίο **ΠΛΗΡΟΦΟΡΙΕΣ** για τρέχουσες σημειώσεις, με ιστορικό **αυτού του πεδίου**· δεν απαιτείται γενική ορατή ιστορία αλλαγών όλων των πεδίων στον καθημερινό πίνακα.

## 5. Αρχικό λεξικό δεδομένων — αντιστοίχιση Access

**Η οριστική λίστα, οι πραγματικοί τύποι και τα legacy codes επιβεβαιώνονται από το πιο πρόσφατο Access/export.** Οι παρακάτω βασικές έννοιες έχουν οριστεί:

| Πεδίο / κατηγορία | Σημασιολογία και βασικοί κανόνες |
|---|---|
| Εσωτερικό `person_id` | Νέο, αμετάβλητο πρωτεύον αναγνωριστικό. |

### 5.1 Δυναμικά πεδία και λίστες

- Ο ORGANOTIKOS προσθέτει **νέες στήλες χωρίς να γράφει κώδικα** (text, checkbox, date, number, dropdown), π.χ. INSTAGRAM, ΔΙΕΥΘΥΝΣΗ.
- Νέα πεδία διαθέσιμα σε πίνακα, καρτέλα, φίλτρα και αναφορές, με σωστό data typing.
- **Ρυθμίσεις → Διαχείριση Δεδομένων & Λιστών**: πανεπιστήμια, τμήματα, διάρκεια σπουδών N, προκαθορισμένες επιλογές, μετονομασία, απενεργοποίηση, σειρά εμφάνισης.
- Μετονομασία τμήματος ή επιλογής **δεν απαιτεί μαζική χειροκίνητη διόρθωση φοιτητών** και δεν σπάει ιστορικές συνδέσεις.

### 5.2 Πυρήνες

- Ο ΠΥΡΗΝΑΣ1 μπορεί να είναι ενεργό στέλεχος, μέλος, εξωτερικό άτομο, κατηγορία, ή «ΑΠΥΡΗΝΩΤΟΙ»· **δεν θεωρούμε πάντα ότι είναι φοιτητής**.
- Παλιά ετήσια ονομασία `ΑΠ23`/`ΑΠ24` κ.λπ. εκφράζει την ίδια κατηγορία, όχι ξεχωριστές ιστορικές οντότητες.
- Κεντρική διαχείριση πυρήνων και προβολή aggregate numbers· δυνατότητα δικαιωμάτων για διαχείριση ενός ή περισσότερων πυρήνων.
- Portal χρήστης μπορεί να υπάρχει χωρίς φοιτητική εγγραφή και να συνδέεται με πυρήνα· έλεγχος μοναδικής ταυτοποίησης owner όπου απαιτείται.
- Η ΠΥΡΗΝΑΣ2 παραμένει ευέλικτη ελεύθερη καταχώριση.

## 6. Η ειδική λειτουργία «ΟΡΓΑΝΩΤΙΚΟ» — Συνεδριάσεις

**Αποτελεί ΚΡΙΣΙΜΗ ξεχωριστή ενότητα, όχι καρτέλα φοιτητή ανά βήμα.** Η συνεδρίαση είναι **πίνακας Access/Excel με πλήρη χειρισμό πληκτρολογίου**.

### 6.1 Δημιουργία και προγραμματισμός

- Νέο Οργανωτικό από κενό, από αποθηκευμένο **ονομασμένο template**, ή από τα **τρέχοντα φίλτρα** του Πίνακα Οργανωτικού.
- Αυτόματη ημερομηνία (επεξεργάσιμη εφόσον χρειάζεται), τίτλος, επιλεγμένες στήλες/διάταξη, sort, συνδυαστικά φίλτρα **1,2,3,4 ή περισσότερα** (`ΚΑΙ`, `Ή`, ομάδες όπου απαιτούνται).
- Φίλτρα π.χ. μη εγγεγραμμένοι ΕΦΕΚΘ + έτος + τμήμα + επιτρεπόμενη κατάσταση, ή οποιοσδήποτε λογικός συνδυασμός.
- Προετοιμασία **πολλών προγραμματισμένων Οργανωτικών** (π.χ. τριών για μία ημέρα), τα οποία εκτελούνται **διαδοχικά**.
- Templates/φίλτρα/προγραμματισμένες συνεδριάσεις μπορούν να μοιράζονται μεταξύ εξουσιοδοτημένων ORGANOTIKOS.
- **Όσο είναι προσχέδιο αποθηκεύονται μόνο οι ορισμοί φίλτρων· οι εγγραφές υπολογίζονται με τα ΤΟΤΕ τρέχοντα δεδομένα ΑΚΡΙΒΩΣ στην έναρξη.**

### 6.2 Μοναδικότητα και σταθερότητα

- **Το πολύ ΜΙΑ συνεδρία σε κατάσταση `ΕΝΕΡΓΟ` ή `ΣΕ ΠΑΥΣΗ` συνολικά**. Δεν επιτρέπεται δεύτερη έως ολοκλήρωση/ακύρωση πρώτης.
- **Ένας ενεργός χειριστής** της ίδιας συνεδρίασης τη φορά, ακόμη κι αν συζητούν πολλά φυσικά πρόσωπα. Όχι πολλαπλοί editors μέσα στην ίδια συνεδρίαση.
- Άλλος εξουσιοδοτημένος ORGANOTIKOS μπορεί **μετά από παύση** να αναλάβει την ίδια συνεδρίαση από το σημείο που έμεινε· κάθε αλλαγή καταγράφει τον χειριστή.
- Στην έναρξη δημιουργείται **σταθερή λίστα αναγνωριστικών φοιτητών**. Αλλαγή του ΠΥΡΗΝΑΣ1 ή άλλου πεδίου που συμμετείχε στα φίλτρα **δεν αφαιρεί γραμμές**.
- Δεν επιτρέπεται **προσθήκη νέου φοιτητή** στη συγκεκριμένη αρχική λίστα· ο επιπλέον εξετάζεται μεταγενέστερα εκτός συνεδρίασης.
- Προσωρινά επιπλέον φίλτρα προβολής/ταξινομήσεις μέσα στη συνεδρίαση είναι ελεύθερα, **χωρίς μεταβολή της σταθερής λίστας**, με «Μόνο ανεξέταστοι» και «Επαναφορά αρχικής προβολής».

### 6.3 Κίνηση και κατάσταση εξέτασης

| Πλήκτρο | Απαιτούμενη συμπεριφορά |
|---|---|
| **Enter** | Commit αλλαγής και κίνηση **στο ίδιο πεδίο/στήλη της επόμενης γραμμής**. |
| **↓** | **Ακριβώς ίδια συμπεριφορά με Enter**. |
| **↑** | Μετάβαση στο ίδιο πεδίο της προηγούμενης γραμμής, με ασφαλή αποθήκευση τυχόν αλλαγής. |
| **Tab** | Commit και επόμενο πεδίο της ίδιας γραμμής. |
| **Shift + Tab** | Προηγούμενο πεδίο της ίδιας γραμμής. |
| **Esc** | Ακύρωση μη αποθηκευμένης αλλαγής. |

- Μετάβαση **προς τα κάτω στην επόμενη εγγραφή** (Enter ή ↓) σημαίνει ότι η προηγούμενη **«ΕΞΕΤΑΣΤΗΚΕ»**, ακόμη κι αν δεν άλλαξε κανένα πεδίο.
- **Δεν υπάρχει «ΠΑΡΑΛΕΙΦΘΗΚΕ»**. Μόνο **Εξετάστηκε / Εκκρεμεί**.
- Ελεύθερη επιστροφή/επανεπεξεργασία οποιουδήποτε εξετασμένου· **μία μοναδική εγγραφή μετράται μία φορά** στον αριθμό εξετασμένων.
- **Απλή κύλιση (scroll) δεν θεωρείται εξέταση.**
- Κατά τη διάρκεια: **ΜΟΝΟ** μικρή ένδειξη προόδου `X / Y`· **κανένα live analytics panel, γράφημα ή μετρητής αλλαγών**.
- **ΟΧΙ ειδική γρήγορη αναζήτηση** μέσα στη συνεδρίαση.

### 6.4 Κύκλος ζωής

- **Προγραμματισμένο → Ενεργό ↔ Σε παύση → Ολοκληρωμένο** ή **Ακυρωμένο**.
- Παύση κρατά τελευταία ενεργή γραμμή/στήλη, κατάσταση εξέτασης, προόδους και ήδη αποθηκευμένες αλλαγές. Μπορεί να συνεχιστεί άλλη μέρα από άλλον ORGANOTIKOS.
- Επιτρέπεται **Ολοκλήρωση πριν εξεταστούν όλες** οι γραμμές, μετά από επιβεβαίωση με αριθμούς εξετασμένων/συνόλου.
- Η **Ακύρωση** τερματίζει συνεδρίαση (π.χ. λάθος φίλτρα), με ρητή επιβεβαίωση, **δεν αναστρέφει ήδη αποθηκευμένες αλλαγές στη βάση**, αλλά κρατά απαραίτητη ιστορική καταγραφή.
- Ολοκληρωμένη συνεδρίαση **κλειδώνει**: δεν μπορεί να δεχτεί νέες μεταβολές με το παλιό session ID, αλλά παραμένει διαθέσιμη για ανάλυση και ως template για νέα συνεδρίαση.
- Ένα προγραμματισμένο Οργανωτικό **δεν καταλαμβάνει** τη μοναδική ενεργή θέση.

### 6.5 Αποθήκευση και σωστός απολογισμός

- Οι αλλαγές **αποθηκεύονται άμεσα στον κανονικό πίνακα**, όχι σε προσωρινό αντίγραφο που αντικαθιστά ολόκληρη τη βάση στο τέλος.
- Αρχική κατάσταση των εγγραφών στην έναρξη + αποθηκευμένες αλλαγές **δεμένες με συγκεκριμένο `session_id`**. Ξεχωριστές αλλαγές τρίτων στον κεντρικό πίνακα **δεν προσμετρώνται** στον απολογισμό συνεδρίασης.
- Αναφορές **«Πριν → Μετά»** ανά επιλεγμένο πεδίο, αριθμός μοναδικών φοιτητών με αλλαγές, πλήθος μεταβολών ανά πεδίο, ιστορική συγκεντρωτική κατανομή όπου επιτρέπεται.
- Διακριτή μέτρηση **ενδιάμεσων edits** από **τελική πραγματική αλλαγή**. Εάν πεδίο τροποποιηθεί πολλές φορές και επιστρέψει στην αρχική τιμή, **δεν εμφανίζεται ως τελική μεταβολή**.
- **Δύο πληθυσμοί αναφοράς** εναλλάξ: (α) μόνο εξετασμένοι, (β) όλοι της αρχικής σταθερής λίστας.
- Οργανωτικός επιλέγει **πριν ΚΑΙ μετά** τη συνεδρίαση δείκτες, ομαδοποιήσεις, γραφήματα/αναλύσεις και μπορεί να αποθηκεύει templates απολογισμού.
- Προαιρετική χωριστή προβολή **«Αναλυτικές αλλαγές»** με αρχική/τελική τιμή ανά φοιτητή/πεδίο για τους κατάλληλα εξουσιοδοτημένους, χωρίς να φορτώνει την κεντρική σύνοψη.
- Ιστορικό συνεδριάσεων με τίτλο, ημερομηνία, status, χειριστές, αρχικό σύνολο, εξετασμένους/ανεξέταστους και απολογισμό.

## 7. Εγγραφές ΕΦΕΚΘ, έτη και ιστορικά

### 7.1 ΕΦΕΚΘ [ΑΠΟΛΥΤΟΣ ΚΑΝΟΝΑΣ]

- Η σημαία `ΕΦΕΚΘ=TRUE` **ΠΟΤΕ δεν γίνεται FALSE αυτόματα**, ούτε στην ετήσια αναβάθμιση, ούτε για IEK, μεταπτυχιακά, N+, αλλαγή σχολής κ.λπ.
- Το TRUE δηλώνει ότι το άτομο είναι επίσημα καταχωρισμένο. Η οριστική διαγραφή από το μητρώο επιβεβαιώνεται **χειροκίνητα** από ORGANOTIKOS, ο οποίος τότε μπορεί να αλλάξει σημαία και ΜΟΝΑΔΙΚΟΣ.
- Κατά την πρώτη επίσημη εγγραφή αποθηκεύονται ημερομηνία (προεπιλογή σήμερα, επεξεργάσιμη) και πηγή (`+`, `ψ2`–`ψ5`, `Μ`).
- Για μη εγγεγραμμένους, τρέχουσα ετήσια ένδειξη μπορεί να αφορά κατάσταση ενδιαφέροντος (`1/2/3`) ή να είναι κενή· μετά την εγγραφή αποθηκεύεται πραγματική πηγή.
- Σε επόμενο έτος κάποιος παραμένει **ΕΦΕΚΘ TRUE** χωρίς υποχρεωτικό νέο code εγγραφής. Επανεγγραφή μετά από επιβεβαιωμένη διαγραφή αποτελεί **νέο ιστορικό γεγονός**.
- Δεν επαναχρησιμοποιούμε παλιές/λανθασμένες ονομασίες κατηγοριών όταν υπάρχουν οι εγκεκριμένοι κωδικοί `ψ2`–`ψ5`.

### 7.2 Περίοδοι / reports

- Υποστήριξη τεσσάρων περιόδων × επιλεγμένες εργάσιμες ημέρες εγγραφών (συνήθως επτά ανά περίοδο), συν ημέρες Α/Β ΓΣ και τυχόν ειδικές περίοδοι.
- Ημερήσια συγκεντρωτικά, διασπάσεις ανά **έτος σπουδών την ημέρα του γεγονότος** (ιστορικά σταθερό), ανά περίοδο και ιστορικές συγκρίσεις.
- Παλιό `ΝΟΥΜΕΡΑ.xlsx` ως δείγμα reports· νέα reports αναπαράγουν υπολογισμούς, όχι απαραίτητα εμφάνιση.
- Ιστορικά aggregates δεν αλλοιώνονται αν κάποιος αποφοιτήσει ή αφαιρεθεί αργότερα από τον ενεργό πίνακα.

### 7.3 Χειροκίνητη ετήσια αναβάθμιση

- **Μόνο με ρητή ενέργεια ORGANOTIKOS**. ΠΟΤΕ αυτόματο yearly cron.
- Προεπισκόπηση, πριν-backup, κανόνες N ανά τμήμα, εξαιρέσεις, έλεγχος, επιβεβαίωση, προστασία από δεύτερη εκτέλεση.
- Κανονικά έτη → επόμενο, μετά N → `Ν1`, `Ν2` κ.λπ.· μεταπτυχιακά `91`, `92` ανά έτος. Λεπτομερείς περιπτώσεις προσαρμόζονται στις πραγματικές διάρκειες.
- Σπουδαστές που τερματίζουν μεταφέρονται σε απόφοιτους (0), εξαιρέσεις τιμητικών (Π) μένουν ενεργές.
- Ετήσια αναβάθμιση **δεν ακυρώνει ΕΦΕΚΘ TRUE**. Παράγει **λίστες υποψήφιων προς έλεγχο**, όχι αυτόματη μεταβολή μητρώου.

### 7.4 Διακύμανση

- Ιστορικές **ημερήσιες αυτοματοποιημένες** και χειροκίνητες στιγμιοληψίες **«ΚΑΤΑΓΡΑΦΗ ΤΩΡΑ»** για επιτρεπόμενα συγκεντρωτικά, με ημερομηνία/ώρα, επιλεγμένο παράθυρο παρακολούθησης και γραφήματα.
- Το παλιό αρχείο `ΔΙΑΚΥΜΑΝΣΗ +Π3Λ 26.xlsx` είναι δείγμα των επιθυμητών χρονοσειρών, όχι δεσμευτική τεχνική υλοποίηση.
- Για δεδομένα που δύνανται να αποκαλύψουν πολιτικές προτιμήσεις απαιτείται περιορισμός σκοπού, ελαχιστοποίηση, πρόσβαση μόνο όπου νόμιμη και αποφυγή εξατομικευμένης πολιτικής στόχευσης.

## 9. Ενοποιημένες λειτουργίες Οργανωτικού / Portal

### 9.1 Απόλυτη απαίτηση ισοδυναμίας

- Το **Οργανωτικό περιέχει 100% των λειτουργιών του Portal**, με το ίδιο επιχειρησιακό αποτέλεσμα και πλήρη χειρισμό, όχι μόνο σύνδεσμο, περίληψη ή «διαχειριστική εποπτεία».
- Ο Οργανωτικός **δεν ανακατευθύνεται ποτέ στο Portal** για ενέργεια.
- Όπου χρειάζεται η ίδια λειτουργία και στα δύο interfaces, επαναχρησιμοποιείται **κοινός κώδικας / υπηρεσία**, όχι αντιγραφή της επιχειρησιακής λογικής.

### 9.2 Κοινές ενότητες

- **Ομάδες και εργασίες**: υφιστάμενα Portal workflows, ανάθεση, παρακολούθηση, checklists/σχόλια/notifications όπου υφίστανται.
- **Οικονομικά**: υφιστάμενοι λογαριασμοί, συναλλαγές, μεταφορές, κατηγορίες, αναμενόμενα, φίλτρα, μηνιαίες συγκεντρώσεις, ιστορικά, audit όπως πράγματι λειτουργούν στον τελευταίο Portal κώδικα.
- **SMS/Μηνύματα**: υφιστάμενες καμπάνιες, λίστες, υπηρεσίες αποστολής, sender IDs, exclusion rules κ.λπ., **και στα δύο UIs**. Δυναμική λίστα ΣΤΕΛΕΧΗ από επιβεβαιωμένο πεδίο ΣΤΕΛΕΧΟΣ του Οργανωτικού και κατάλληλα δικαιώματα πρόσβασης.
- **Εκδηλώσεις / Portal administration**: πλήρης λειτουργικότητα της υπάρχουσας εφαρμογής.
- **Μέλη**: κύρια διαχείριση Οργανωτικού· Portal μόνο όπου δικαιούχος έχει ειδική εξουσιοδότηση.
- **Bluepass**: κύρια διαχείριση Οργανωτικού· Portal μόνο όπου δικαιούχος έχει ειδική εξουσιοδότηση.
- **Προσφορές / Newsletter**: κύριες ενότητες Portal, αλλά **εξίσου πλήρως λειτουργικές μέσα στο Οργανωτικό** για ORGANOTIKOS.

### 9.3 Σύνδεση Members / Bluepass / φοιτητή

- Οι ηλεκτρονικές αιτήσεις μπορεί να αφορούν υπάρχον φοιτητή ή πρόσωπο εκτός της βάσης.
- Κατά το matching: προτάσεις μόνο, **επιβεβαίωση ανθρώπου**, optional πρόταση ενημέρωσης στοιχείων με preview, όχι αθόρυβη αντικατάσταση του Οργανωτικού.
- Εγκριμένη/επιβεβαιωμένη ταύτιση Members → **ΜΕΛΟΣ Πρωτοπορίας** TRUE· Bluepass → **BLUEPASS** TRUE. Τα `ΜΕΛΟΣ` και `ΕΦΕΚΘ` είναι διαφορετικές έννοιες.
- Αίτηση για άτομο εκτός πίνακα **δεν δημιουργεί αυτόματα φοιτητική εγγραφή**. Δυνατότητα επιλογής «Προσθήκη στον πίνακα» από ORGANOTIKOS.
- Από διαχείριση Members/Bluepass μπορεί να ανοίγει η συνδεδεμένη φοιτητική καρτέλα, εφόσον επιτρέπεται.

## 10. Χρήστες, ρόλοι, TOTP και ασφάλεια [ΑΠΟΦΑΣΙΣΤΗΚΕ]

### 10.1 Μία ταυτότητα, κεντρική διαχείριση

- **Ένας λογαριασμός/credentials** για Portal + Οργανωτικό.
- **Νέοι λογαριασμοί δημιουργούνται, μαζικά εισάγονται, διαχειρίζονται, επαναφέρονται και διαγράφονται ΜΟΝΟ μέσα από το Οργανωτικό.** Όχι ξεχωριστή δημιουργία στο Portal ή στο dashboard ιστοσελίδας.
- Οι παλιοί λογαριασμοί θα μεταφερθούν μετά από inventory, reconciliation και σχέδιο ενεργοποίησης· να αποφεύγονται διπλά accounts.
- `ORGANOTIKOS`: **όλοι οι ORGANOTIKOS απολύτως ισότιμοι**, πλήρη δικαιώματα Οργανωτικού **και `ADMIN` στο Portal**.
- `MASTER`: λεπτομερή δικαιώματα **στο Οργανωτικό θα αποφασιστούν όταν υπάρχει λειτουργική εφαρμογή**· Portal role **`ADMIN` ή `ΗΓΕΣΙΑ` επιλεγόμενο ανά χρήστη**. Ασφαλής default deny για μη αποσαφηνισμένες αρμοδιότητες.
- Άλλοι ρόλοι **μόνο Portal**, χωρίς Organotiko: `ADMIN`, `ΗΓΕΣΙΑ`, `ΣΥΝΤΟΝΙΣΤΗΣ`, `ΜΕΛΟΣ`.
- **Granular δικαιώματα ανά module**: μέλος Portal μπορεί να έχει ρητή άδεια Bluepass, Newsletter κ.λπ. χωρίς να γίνει γενικός Portal ADMIN.
- **Προσοχή**: Portal ADMIN **δεν αποκτά** αυτόματα δικαίωμα εισόδου ή πρόσβασης σε δεδομένα Οργανωτικού.

### 10.2 Είσοδος και recovery

- **Μόνο στο Οργανωτικό: ΥΠΟΧΡΕΩΤΙΚΟ TOTP Authenticator (2FA)** για κάθε χρήστη που επιτρέπεται να μπει. Δεν επαρκεί απλό UI gate· τα δεδομένα προστατεύονται και server-side/RLS.
- Portal: κοινός λογαριασμός, χωρίς υποχρεωτικό TOTP για τη δική του λειτουργία.
- Login με username/password, έπειτα κωδικός Authenticator για πρόσβαση στο Οργανωτικό· συμβατές εφαρμογές Google/Microsoft ή άλλες TOTP.
- Κάθε νέος χρήστης αποκτά **προσωρινό κωδικό και υποχρεωτική αλλαγή στην πρώτη σύνδεση** (και σε bulk creation). Εξουσιοδοτημένος ORGANOTIKOS μπορεί να εκδίδει νέο προσωρινό κωδικό με επαλήθευση, χωρίς ποτέ αποκάλυψη του παλιού.
- Για Organotiko χρήστη, πρώτη είσοδος ενεργοποιεί TOTP, εμφανίζει **10 recovery codes μιας χρήσης**, **μόνο μία φορά**, χωρίς αποστολή με email/SMS· ο ίδιος τα φυλάσσει ασφαλώς. Στη βάση αποθηκεύονται μόνο ασφαλείς μη αναστρέψιμες επαληθεύσιμες αναπαραστάσεις, όχι plaintext.
- Εναλλακτική ελεγχόμενη **επαναφορά TOTP από άλλον ισότιμο ORGANOTIKOS**, με αυστηρή επαλήθευση ταυτότητας και καταγραφή. Ανάκτηση κωδικού **δεν παρακάμπτει** 2FA.
- Recovery codes δεν είναι κατ’ ανάγκην built-in Supabase feature· απαιτούν ασφαλή ειδική υλοποίηση και δοκιμές πριν production.

### 10.3 Διαγραφή λογαριασμού

- **Όχι «απενεργοποίηση» ως κανονική διαδρομή αποχώρησης**. Επιλογή **«Οριστική Διαγραφή Λογαριασμού»** με εμφανή επιβεβαίωση.
- Κατάργηση Auth identity, roles, πρόσβασης και ενεργών συνεδριών/refresh· μην υποθέτουμε ότι απλή διαγραφή Auth user ακυρώνει ήδη εκδομένα JWT αμέσως· σχεδιάζονται πρόσθετοι έλεγχοι ανάκλησης.
- Αν επιστρέψει το πρόσωπο στο μέλλον, δημιουργείται **νέος λογαριασμός**.
- **Διαγραφή λογαριασμού ΔΕΝ διαγράφει ποτέ αυτόματα την ανεξάρτητη εγγραφή φοιτητή, Πυρήνα ή επιτρεπόμενα ιστορικά δεδομένα.** Ιστορικά logs ελαχιστοποιούνται/διατηρούνται μόνο όσο νόμιμα αναγκαίο.

### 10.4 Ασφάλεια σε επίπεδο δεδομένων

- Υποχρεωτικό RLS για εκτεθειμένους πίνακες, module-level authorization από αξιόπιστο backend, όχι μόνο κρυμμένα κουμπιά.
- Authorization claims **όχι** από self-editable user metadata. Admin/secrets αποκλειστικά server-side.
- Όπου απαιτείται οργανωτική πρόσβαση, ο έλεγχος περιλαμβάνει ισχύον `ORGANOTIKOS`/`MASTER` entitlement και **επαληθευμένη TOTP/AAL2**.
- Διαχωρισμός public website forms από protected administration, rate limits, input validation, περιορισμένο disclosure, secure audit.
- **Ιδιαίτερα ευαίσθητα πεδία** (πολιτική οργάνωση, πρόθεση, πολιτικές κατηγορίες, αποτελέσματα) απαιτούν τεκμηριωμένη νόμιμη βάση, περιορισμό πρόσβασης, retention και DPIA όπου απαιτείται. Όχι αυτοματοποιημένη εξατομικευμένη πολιτική στόχευση ή πρόβλεψη πολιτικής συμπεριφοράς.

## 12. Ubuntu Server, backups και συντήρηση

- Αυτόματη εκτέλεση **κρυπτογραφημένων backups από Supabase → Ubuntu Server** και ξεχωριστή offsite/ανεξάρτητη δεύτερη αντιγραφή.
- Περιλαμβάνει database schema/data, απαραίτητη κατάσταση Auth και άλλους πόρους που χρειάζονται για λειτουργική επαναφορά· για Supabase Storage οργανώνεται **ξεχωριστό backup των πραγματικών objects** όπου χρησιμοποιούνται.
- Καθορισμός retention, rotation, integrity checks, αποτυχίες με ειδοποίηση, τακτικά **δοκιμαστικά restore**.
- **Χειροκίνητο backup από Οργανωτικό**, εμφάνιση επιτρεπόμενων backups και προστατευμένη διαδικασία restore με ισχυρή επιβεβαίωση, backup-current-before-restore και ασφαλή recovery runbook.
- Scheduled jobs: προϋπολογισμοί στατιστικών, ημερήσια snapshots σε ενεργό monitoring window, report generation, επιλεγμένες SMS εργασίες, housekeeping.
- Ο server δεν αναλαμβάνει realtime CRUD και δεν μπλοκάρει login/app όταν είναι προσωρινά εκτός λειτουργίας.
- **Ετήσια αναβάθμιση ΔΕΝ γίνεται μέσω cron**· μόνο χειροκίνητα.
- Σχεδιασμός για απρόσμενη διακοπή job, idempotency, queue, retries και ασφαλή server-only credentials.
